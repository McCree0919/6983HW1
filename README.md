# TRANSFER / 01 - Physics Chamber

Coding Assignment #1. Unity **6000.3.24f1**, Universal Render Pipeline, Input System.

## Run and play

1. Open this repository as a project in Unity 6000.3.24f1.
2. Open `Assets/Scenes/PhysicsChamber.unity`, then press **Play** and focus the Game view.
3. Use **WASD** to move the cyan Actor. W moves toward the top of the maze.
4. Enter the coral sensor in the northwest alcove to remove the coral roadblock.
5. Push the gold Payload through the north opening in the first divider, south
   through the middle corridor, and through the south opening in the second
   divider. Push it north into the green DepositZone in the east corridor.
6. Use **R** or **Restart** to restore the starting positions, roadblock, sensor,
   success state, and timer.

The chamber is generated by `ChamberBuilder.Awake` when Play starts. The saved
scene initially contains only the generator, so an empty Edit Mode chamber is
expected. Geometry, spawn positions, materials, camera, and lights are defined in
`Assets/PhysicsChamber/ChamberBuilder.cs`. PhysicsChamber is the first enabled
scene in Build Settings; SampleScene is retained separately.

The initial alcove wall requires moving the crate around its east end. Leave
space around the crate to get behind it before each turn. The Actor cannot carry,
teleport, or pull the Payload; transport happens through Rigidbody collisions.

## Requirements and behavior

| Requirement | Implementation |
| --- | --- |
| WASD Actor and maze | `ActorController.Update` reads keyboard input and normalizes diagonals. Outer walls and alternating dividers form an S-shaped route. |
| Physics updates | `ActorController.FixedUpdate` applies bounded forces toward a target planar velocity. Gameplay does not move either body by assigning its Transform. |
| Sensor removes roadblock | Only the registered Actor can activate `ChamberSensor`. `ChamberRun.Unlock` disables the roadblock and its collider, changes the sensor color, and logs the event once. |
| Push after unlocking | The registered Payload must enter DepositZone after unlocking. A crate already overlapping the zone before unlock must completely leave and enter again. |
| Guarded success | `DepositZone` requires the Payload's entire XZ collider footprint inside the zone. The Actor, partial overlaps, and entries from an earlier restart cannot win. |
| Elapsed time | The timer starts at Play, resets on Restart, and freezes on the first successful deposit. The success log includes elapsed seconds. Editor pause and `timeScale` pause this game-time timer. |
| Different physics | Actor and Payload use different mass, linear damping, and friction values, shown below. |

| Setting | Actor | Payload |
| --- | ---: | ---: |
| Mass | 2 | 3.5 |
| Linear damping | 1.4 | 0.65 |
| Static/dynamic friction | 0.05 | 0.18 |

The floor friction is 0.45. Contact materials use Minimum friction combining and
zero bounce. The Actor uses a maximum drive force of 38 and a target speed of 4.5.
Both bodies retain gravity, freeze rotation, and use continuous dynamic collision
detection and interpolation. Crate bands are decorative and have no active
colliders. Restart clears linear and angular velocity as well as trigger state.

## Reflection

### 1. What must be true for success, and can the player cheat?

The Actor must first activate the sensor so the roadblock is physically removed.
The registered Payload must then enter the DepositZone and fit completely inside
its XZ bounds before the run can finish. Touching the pad with the Actor or only
the front of the crate does not count. Parking the crate there before unlocking
also fails until it leaves and enters again after unlock. Physical walls, frozen
rotation, and the lack of a jump action prevent the intended controls from
bypassing the maze over a divider.

### 2. What unexpected behavior occurred, and what changed?

In the initial Play Mode checks, both the Actor and Payload fell through the
floor even though their spawn coordinates were correct. Runtime inspection
showed that the Default layer was ignoring collisions with itself. The project
used a collision-matrix serialization that the installed Unity version did not
load as intended after a version change. I converted that setting to a compatible
format with Default-to-Default collisions enabled. The regression checks now
explicitly test that both bodies remain supported by the floor after spawning
and restarting.

### 3. What design tradeoff did you make?

I chose a heavier Payload with low contact friction so the Actor can push it
using limited forces. Movement still uses physical acceleration and collision
contacts instead of teleporting the crate. Freezing rotation prevents the crate
from tumbling or becoming diagonally wedged in a passage. This sacrifices some
realistic box motion in exchange for more predictable control.

### 4. What is the weakest part, and what would you change first?

The weakest part is recovering after the crate is pushed tightly against a wall.
Because the Actor cannot pull, there may be no room to get behind it again.
Restart restores a playable state but discards progress and resets the timer.
I would first playtest the turning spaces with several players and widen corners
that repeatedly trap the crate while keeping transport entirely physical.

## Verification

Verified on **2026-09-30 with Unity 6000.3.24f1**: all **48 automated Play Mode
checks passed** in a separate project copy. The run finished with
`CHAMBER VERIFICATION PASSED`, with no C# compile errors or managed exceptions.
Desktop (1280 x 800) and portrait (480 x 800) camera captures were also inspected.

`Assets/PhysicsChamber/Editor/ChamberVerification.cs` supplies the automated
Play Mode runner through `PhysicsChamber.Editor.ChamberVerification.RunBatch`.
The runner is restricted to an isolated batch project because it opens the
assignment scene and exits the Editor when finished. Its checks cover spawn
positions and floor support, all four WASD keys, trigger ordering, physical
roadblock collision and removal, deposit containment, one-shot timing and logs,
and restart behavior. The route check pushes the Payload through both divider
openings using simulated keyboard input through the actual Actor controller.
It repositions the Actor between corners to isolate each push; it never
teleports the Payload during that route, so this proves the route's physical
feasibility rather than a complete human-style navigation playthrough.

Run against a separate copy of `Assets`, `Packages`, and `ProjectSettings`:

```text
Unity.exe -batchmode -projectPath "<validation-project>" -executeMethod PhysicsChamber.Editor.ChamberVerification.RunBatch -logFile "<validation.log>"
```

Do not add `-quit`: the runner exits after its asynchronous checks finish.
If this project was open before the physics-settings fix, restart Unity to
reload the corrected collision matrix, then reopen `PhysicsChamber.unity`.

Manual acceptance: play the full route with WASD, confirm one roadblock-removal
log and one timed success log, then restart and repeat. Control feel and keyboard
playtesting are separate from automated state and physics checks.
